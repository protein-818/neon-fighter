## 1. ねらい

ゲーム本体は、JavaScript を1つの HTML ファイル（約262KB）に入れた形で、Claude のアーティファクトの上で作っている。キャラが11人になり、次の困りごとが大きくなった。

- 更新のたびに全体を読み書きするので、遅く、使用枠を多く使う。
- どこを変えたかが残らず、前の版に戻しにくい。
- 本体はアーティファクト、公開物は GitHub と2か所にあり、公開のたびに取り出しと変換が要る。

そこで、次の2つを行う。**言語は変えない。ゲームの動きも変えない。**

1. 本体の正本を、アーティファクトから GitHub のリポジトリ `protein-818/neon-fighter` に移す。
2. 本体を複数のファイルに分け、公開するときに1つにまとめる。以後の開発は Claude Code で行う。

## 2. 変えないもの

- 遊びの中身（数値、CPU、見た目、音、操作）。**引っ越しの間は機能の追加と調整をしない。**
- 公開ページの URL と、公開される `index.html` が1ファイルであること。
- 公開側との取り決め: 外付け部品が読む名前（`mode` `paused` `tut` `SPECT` `A` `B` `win` `lv` `LV` `CH` `ch` `cv` `VS2` `LANG` `TR` `NF_INPUT`）、キーの受け方、script が1つであること、ファイル末尾の形、`NFA` の3つの呼び出し。
- 保存データ（`nf2_*`、`nf_aud2`）。遊んでいる人の戦績や設定が消えないこと。
- 外付け部品（`analytics.js` `gamepad.js` `site.js` `privacy.html` `og.png` `favicon.svg`）。

## 3. 進め方（4段階。1段階ずつ確かめてから次へ進む）

使用枠を守るため、**1日に1段階**を目安にする。終えたら連絡ノートに結果を書いて止まる。

## 4. 開発側への依頼

### 4-1. 段階0: 引き継ぎの準備（いまの開発側チャットで行う）

いまの開発側チャットの作業場にある道具と知識は、チャットの外からは読めない。引っ越しの前に外へ出してほしい。

1. **確かめる道具を渡す。** 総当たりを回すスクリプト、乱数と時刻を固定して前後を比べるスクリプト、Playwright の通し試合と画像比較。ファイルとしてマネージャーに渡すか、プロジェクトに `資料_開発_02_検証の道具` として置く。使い方（コマンド、難易度、試合数、かかる時間）を添える。
2. **引き継ぎ書を書く。** `資料_開発_03_引き継ぎ` として、次を書く。
   - ソースの中の並び（どの区分がどの順に書かれているか）。`02` §3 の表を、実際の並び順に直したもの。
   - 読み込み時に走る処理と、その順番に意味がある箇所（例: 全技フレームの×1.15、リーチ+10、`cut`・`blunt` の付与）。
   - 分けるときに危ない箇所（定義より前に使っている変数、同じ名前の使い回し、`p2w()` の `ch` の入れ替えなど）。
   - 新しいキャラや仕組みを足すときに触る場所の一覧（`CH` `LOOK` `STN` `PERS` `LINES` `TPOSE` `EN` など）。
3. **`03` がアーティファクト Version 64 と同じであることを確かめる。** 違いがあれば連絡ノートに書く。

### 4-2. 段階2: 確かめる道具をリポジトリに入れる（Claude Code で行う）

1. 段階0 の道具を `tools/` に入れ、リポジトリのソースを相手に動くようにする。
2. 分ける前の Version 64 で**基準**を記録する。
   - 乱数を固定した総当たり（11人、3難易度）の試合結果。
   - 決まった場面の画面（タイトル、キャラ選択、対戦設定、試合中、結果、ポーズ、トレーニング、2人対戦、英語表示。PC とスマホ横持ち）。
3. 1つのコマンドで「まとめる → 基準と比べる」が回るようにする。
4. 最初に、このセッションからプロジェクトの進行表と連絡ノートを読み書きできるかを確かめ、結果を知らせる（§8）。

### 4-3. 段階3: 本体をファイルに分ける（Claude Code で行う）

**分け方の指定**

- JavaScript を、`02` §3 の区分をもとに十数個のファイルに分ける（例: `data-chars` `data-moves` `data-look` `consts` `flow` `combat` `limbs` `rival` `ai` `gimmicks` `pose` `draw-figure` `draw-fx` `screens` `training` `input` `vs2p` `lang` `sound`）。区切りは開発側の判断でよい。
- まとめ方は、**決まった順にファイルをつなげて1つの script にする**だけにする。今のコードは、外付け部品から名前で読まれる変数（`mode`、`A`、`B` など）を前提にしている。部品ごとに名前を閉じ込める方式（ES モジュール、バンドラー）にすると、取り決めが壊れる。
- つなげる順番は1つのファイル（例: `src/order.txt`）に書く。
- HTML の枠（`<head>`、CSS、タッチ UI の要素）は `src/shell.html` のように別に持つ。
- TypeScript への移行と、コードの書き直しはこの依頼に含めない。

**受け入れ条件**

1. 分けた直後、まとめたファイルが分ける前と**1文字も違わない**（切って、つなげ直しただけであること）。
2. 乱数を固定した総当たりの結果が、基準と完全に同じ。
3. 決まった場面の画面が、基準と画素単位で同じ。
4. 取り決め（§2）が守られている。公開側の `tools/apply_patch.py` の確認（`NFA` の呼び出しが1回ずつ、など）が通る。
5. 保存データを入れた状態で開いて、戦績・色・設定・言語が引き継がれる。
6. リポジトリに `CLAUDE.md` があり、指示欄の共通ルール、取り決め、まとめ方、確かめ方、文書の置き場が書かれている。
7. `01`・`02` に、新しい構成（ファイルの一覧、まとめ方、確かめ方）が書かれている。

受け入れ条件1は、分ける作業そのものの確認に使う。その後に整形や並べ替えをする場合は、2と3で確かめる。

## 7. うまくいかなかったとき

- 段階4 が終わるまで、アーティファクト Version 64 とプロジェクトの `03` はそのまま残す。どの段階で止まっても、今のやり方に戻れる。
